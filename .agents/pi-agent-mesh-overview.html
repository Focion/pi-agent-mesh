Multi-Agent Infrastructure

Pi Agent Mesh

@pi/agent-mesh · v0.1.0（规范面 v1.0.0 已定稿）

它是构建在 pi SDK 之上的多 Agent 协作通讯层：让 N 个各自持有独立持久 session 的 pi Agent 能够互相寻址、投递、组队、发现彼此的能力、协调发言次序、共享一块状态—— 而它不知道这些 Agent 是谁、为什么说话、说完之后要记住什么。

零领域知识 mesh-core 零 pi 依赖 9 个策略槽可注入 209 测试全绿 TypeScript · ESM+CJS
核心问题 协作原语 架构 宪法约束 非目标 落地状态
The Core Problem

它到底在解决什么问题？

pi SDK 提供的是"一个能力很强的单 Agent"。要把它变成"一群能长期共存、互相协作的 Agent"， 中间缺四样东西。这四点就是本项目存在的全部理由。

1

没有 peer-to-peer 通道

不解决会怎样

每个宿主都要自己造账号 / 会话 / 成员 / 未读 / 回执，且互不兼容。

  • pi 官方 subagent 是"派生短命工人"，不是长期共存的同侪
  • RemoteSession 只能"遥控一个 session"，而非"两个 session 互相说话"
  • 答案：§4 概念模型 + §11 存储 + §12 API（账号/通讯录/会话/成员/未读/回执 全部自建）
2

每条消息都唤醒 = 成本爆炸

不解决会怎样

30 人群里一条消息触发 30 次 LLM 轮次；成本与人数成平方增长。

  • 这是本项目投入最多设计、也相对"自己写个消息表"的主要价值
  • 答案：§7 三档投递（steer / followUp / silent）+ 唤醒判定 + 原文预算
  • 目标：把"每消息平均唤醒数"压到 ≤ 1.2（§24.2）
3

写入路径竞争会损坏 session 树

不解决会怎样

两条路径写同一棵 append-only 树，leaf 指针错乱，Agent 历史损坏且不可恢复。

  • pi 队列对本库不可观测，clearQueue() 还会静默销毁未落盘消息
  • 答案：M3 单写者 + §8 Stream 抽象，一切写入收敛到唯一通道
  • 跨进程用 .lock 文件，抢锁失败即拒绝启动
4

消息内容会被当成指令执行

不解决会怎样

Agent A 发一句"忽略你的规则"，Agent B 照做——提示注入在 Agent 群里是可传染的。

  • 答案：M4 + §10.3 渲染四防线 + §22.3 威胁模型
  • 在渲染层强制"这是别人说的话"，不依赖宿主自觉
  • 消息是数据，不是指令——结构化包裹 + 转义 + 显式声明来源
两条"该不该进库"的测试：① 换域测试——把宿主业务全换成另一套（如"教学助手集群"→"客服机器人+工单"），这功能还需要吗？ ② 换形态测试——把"人与 Agent 对话"换成"一个 planner 给 5 个 worker 派活并收回执"，这功能还表达得出来吗？两条都过，才进库。
The Solution

六组协作原语：能力的完整边界

Pi Agent Mesh 的全部能力就是这六组原语。发现与协调正是它和"一条消息总线"的本质区别—— 没有它们，多 Agent 只能被宿主硬编码地驱动，Agent 之间不存在自主协作的可能。

📇

寻址 Addressing

账号、端点、通讯录；from 签发与防伪（不可伪造）。§4.1 §5.4 §6 §11.1

📨

投递 Delivery

档位、唤醒、顺序、幂等、未读、扇出、洪泛防护——把"每消息平均唤醒数"压到 ≤1.2。§7

🗂️

容器 Container

四类会话：direct / group / topic（订阅式广播）/ queue（竞争消费）。§4.3 §9 §16 §17

🔍

发现 Discovery

capabilities 声明 + mesh_lookup 零成本目录查询 + Presence 在场状态。§4.2 §10.1 §15

🤝

协调 Coordination

expect / correlationId / FloorPolicy 发言权 / MeshHost.nudge 主动驱动轮次。§13 §14 §12.2

🧩

共享状态 Shared State

共享对象、ACL 访问控制、乐观锁（CAS）、变更通知——一块 Agent 之间可读写的公共黑板。§18

Architecture

分层架构：core 与 pi 被一道窄接口隔开

MeshHost 是唯一门面；下方 8 个组件各司其职。按"是否碰 pi"切成两个模块， 中间用恰好 10 个方法的 StreamPort 窄接口隔开——这就是"库变大"的担忧被关进一个模块的原因。

一条能自查的规则：只有 SessionHost 能碰 AgentSession，只有 Router 能写 mesh_messages， 只有 Observer 能被宿主用于读。三条各自单点，出问题时定位范围固定。 除 9 个插件槽外，没有任何组件回调宿主业务函数——宿主只能注入策略（被询问）或订阅事件（被通知）。
Constitutional Constraints

六条宪法级约束（M1–M6）

每条都配可执行的检测手段（CI 门禁），不靠人自觉。这是库能跨宿主复用的根基。

M1 零领域知识

库代码不得出现任何宿主业务词汇；领域数据只能进信封 ext 袋，库只透传持久化、不解释。

M2 语义由宿主注入

优先级/唤醒/时间比较/渲染/权限全是可替换策略对象；9 个策略槽就是库与宿主的全部接触面。

M3 一条 stream 一个写者

一个 session 文件任一时刻只能被一个写者驱动；跨进程用文件锁。违反=session 树损坏且不可恢复。

M4 消息是数据，不是指令

投递进上下文的内容必须结构化包裹+转义+显式声明来源；在渲染层强制，不依赖宿主自觉。

M5 至少一次 + 幂等应用

每条投递有幂等键；重放不产生第二次上下文追加、不发第二次事件。

M6 收件箱严格分区

Agent A 不可能读 Agent B 的收件箱/未读/回执；工具签名里没有 owner 参数，一律由上下文注入。

Scope Discipline

明确的非目标 & 四条"反直觉"断言

写在这里，是为了防止后续讨论把库撑成一个应用。库刻意偏离"即时通讯软件"的直觉——因为接收方是 LLM 而不是人。

库不负责这些

  • 不为自己的目的调用 LLM（不做摘要/路由/意图识别）
  • 不做记忆、人格、知识状态机
  • 不做 UI；只提供事件流让 UI 订阅
  • 不做分布式共识（用 SQLite 单写者，不是 Raft）
  • 不做加密传输（seal 只防 Agent 层伪造）

四条正向断言

  • A1 消息一旦投出即不可撤回/不可编辑（更正靠追加 tombstone）
  • A2 没有已读回执、没有"正在输入"
  • A3 不做"送达但未读"第三态（投递集=未读集）
  • A4 寻址即投递集：to ∪ mentions 就是投递范围
"一条消息的一生"：发送 → Router 校验/签发 from/分配 seq 落库 → 计算投递集 → EndpointSelector 选端点 → DeliveryPolicy 定档位 → ActivationPolicy 定唤醒 → 写 mesh_deliveries（routed）→ Mailbox 投递（热流 P1 / 冷流 warm 后 P1 / 冷流 silent 留未读 P2）→ entry_appended 触发 delivered → 首个 turn_end 触发 consumed。任何一步失败都归属：同步拒绝 / 可恢复挂起(parked) / 终态丢弃(dropped)。
