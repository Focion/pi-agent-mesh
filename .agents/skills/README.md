# skills — 项目技能

存放**本项目专属**的可复用操作流程。与 `notes/` 的区别：notes 记录「知道了什么」，skills 记录「怎么做一件事」，且写成能被 Agent 直接照着执行的形式。

## 目录约定

一个技能一个子目录，目录名用 kebab-case：

```
skills/
└── <skill-name>/
    ├── SKILL.md        # 必需：技能说明与执行步骤
    ├── scripts/        # 可选：可执行脚本
    ├── assets/         # 可选：模板、配置样例
    └── references/     # 可选：需要时才读的长文档
```

## SKILL.md 格式

以 frontmatter 开头，`name` 与目录名一致，`description` 决定这个技能什么时候被用到——写清**做什么**和**何时触发**（包含用户可能说的关键词）：

```markdown
---
name: <skill-name>
description: >
  <做什么>。当用户要求 <场景 A>、<场景 B>，或提到 <关键词> 时使用。
allowed-tools: Bash, Read, Write   # 可选，限制可用工具
---

# <技能标题>

## 何时使用

<适用与不适用的边界。>

## 前置条件

<需要的环境、权限、依赖。>

## 执行步骤

1. <一步一个动作，给出可直接运行的命令>
2. <...>

## 校验

<怎么确认做成了。>

## 常见问题

<报错现象 → 原因 → 处理。>
```

## 写作要点

- **可执行优于描述性**：给确切命令和文件路径，不要写「配置一下相关参数」。
- **保持简短**：SKILL.md 控制在一屏内能读完；长内容拆到 `references/` 并在正文写明何时去读。
- **幂等**：脚本重复执行不应破坏已有状态；有破坏性操作时先确认或提供 `--dry-run`。
- **可校验**：给出判断成功的标准（命令输出、文件存在、接口返回）。
- **一技能一件事**：涉及多个独立流程时拆成多个技能，互相引用。

## 维护

- 技能失效时先修，确实不再需要再删除目录（技能是操作流程，无历史价值，不进 `notes/archive/`）。
- 项目命令、路径变更后，检查 skills 里引用的命令是否仍然可用。
