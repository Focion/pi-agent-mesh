## 方案概述

W01 的三个「生产可行确认点」用真实 pi 1.1.0 + faux（无网、无真实 LLM）探明，各自固化为一条探针测试（当作 1.1.0 行为锁，升版本后按 CT-F 规则复核）：P2 最终输入是否可确认、hook 覆盖矩阵、磁盘 session create/open 是否确定。结论：**三者全部可行，无 blocked**，W08/W11/W13 的确认点由此落定。

证据来源：`tests/pi/probe-p2-input.test.ts`、`tests/pi/probe-hooks.test.ts`、`tests/pi/probe-disk-session.test.ts`（均通过）。机制推断均对照 `node_modules/@earendil-works/pi-coding-agent/dist/core/` 源码（`extensions/runner.js`、`sdk.js`、`session-manager.js`、`agent-session.js`）。

## P2 最终输入可确认（W08 确认点）

**结论：可确认。** 确认点 = 扩展 `context_with_system` 钩子（或捕获 `streamSimple` 的 `context.messages`）。

机制（`runner.js` `emitContext` 两阶段 + `sdk.js` `transformContext`）：

1. `Agent.transformContext` → `runner.emitContext(messages)`，在每个 LLM 调用前执行。
2. ① 每个 `context` 处理器只看非 system 消息；注入器 `injectContext`（`stream-port.ts`）在此追加一条 `role:"custom"` / `customType:"mesh.inbox"` 消息，Pi 用 `restoreSystemMessages` 把 system 前缀（若有）钉回。
3. ② 每个 `context_with_system` 处理器看到「全部 context 处理完 + system 已恢复」的完整 transcript，其输出原样作为模型输入。

探针结果：`context` 注入 sentinel → `context_with_system` 观测到 sentinel 以 `mesh.inbox` custom 消息形态、恰一条存在于最终 transcript。**注入体在进入模型前可被观测**，且可被按 `customType` 定位。空转（不起轮）不产生模型调用 ⇒ 观测点为零次（确认点绑定真实 LLM 调用，不是注入即可见）。

## Hook 覆盖矩阵（W08/W11 选点）

单轮（sendCustomMessage + triggerTurn，faux 文本回复）：

| 钩子 | 体系 | 点亮 | 载荷要点 |
| --- | --- | --- | --- |
| agent_start / agent_end | 会话 + 扩展 | ✓ | 会话事件记 `type`；扩展 `agent_end` 带 `messages` |
| turn_start / turn_end | 会话 + 扩展 | ✓ | `turnIndex`/`timestamp`；`turn_end` 带 `message`、`toolResults`、`messageEntryId`、`toolResultEntryIds` |
| message_start / message_end | 会话 + 扩展 | ✓ | `message`（含 role）；`message_end(custom)` 是 §8.4 镜像触发点 |
| agent_settled | 会话 + 扩展 | ✓ | 仅 `type` + `aborted`（F2 复核不变） |
| agent_before_settle | 扩展 | ✓ | boundary 语义（可追加条目） |
| context / context_with_system | 扩展 | ✓ | `messages`；见上节 |
| entry_appended | 会话 | ✗（普通起轮） | 只在工具上下文的 `appendCustomEntry`、boundary drafts 等路径发出 |
| before_agent_start | 扩展 | ✗ | 只走「用户 prompt 提交」路径（sendUserMessage/prompt）；mesh 投递经 sendCustomMessage 不触发（I19） |
| before_provider_request | 扩展 | ✗（faux） | prepareRequest/HTTP 路径；faux streamSimple 直连不点亮 |
| after_provider_response | 扩展 | ✓（faux） | onResponse 包装流也执行 |
| provider_stream_event | 扩展 | ✗（faux） | 只对解析后的 provider 原始流事件；faux 产出整条 assistant 消息 |
| tool_call / tool_result / tool_execution_start·update·end | 扩展 | 见下 | `toolCallId`/`toolName`/`args`/`result`/`isError` |

tool call 场景（注册自定义工具 + `fauxToolCall` 脚本）：`tool_call`、`tool_execution_start`、`tool_execution_end`、`tool_result` 全部点亮。

**选点结论**：W08 的上下文确认点用 `context_with_system`；W11 的轮次归因仍用会话事件 `turn_end` + `entry_appended`（仅 note/boundary 路径）/`message_end(custom)`，provider HTTP 钩子不能作为 faux 探针下的确认点。

## 磁盘 session create/open 确定（W13 确认点）

**结论：可行且确定。** `getSessionFile() ?? getSessionId()` 约定在 1.1.0 下成立。

证据（`session-manager.js`）：

1. `SessionManager.create(cwd, sessionDir)` 在 `newSession()`（persist=true）立即设 `sessionFile = <sessionDir>/<timestamp>_<sessionId>.jsonl` —— **create 点即返回非空路径**，`?? getSessionId()` 永不回退到 id；路径落在隔离 sessionDir 内、含本 sessionId。
2. 文件本体延迟到首条 user/assistant 消息后才写出（`_hasConversation` 门；setup 条目不落盘）。探针实测：起轮前文件不存在，起轮后存在。
3. `open(同路径, sessionDir, cwd)` 按 header 恢复**同一 sessionId** 与同一 `getSessionFile()` —— 重开点确定（mesh 存的就是路径，按路径恢复）。
